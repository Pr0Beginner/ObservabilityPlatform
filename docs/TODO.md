# Observability Platform 业务范围与实施路线

## 运行模式

- `local`：用于本地开发和单元测试。日志、故障、诊断任务等数据保存在当前 JVM 内存中，日志批次在进程内直接处理，不依赖 Kafka、MySQL 和 Elasticsearch；应用重启后数据丢失，不用于生产环境。
- `external`：用于真实部署。Kafka 承担异步消息传递，MySQL 保存故障、诊断任务、统计窗口、通知和死信记录，Elasticsearch 保存并检索日志。

这两个名称是本项目的适配器运行模式，与 Go `sync.Map` 的 `read`、`dirty` 和 `misses` 无关。Java 内存适配器主要使用 `ConcurrentHashMap`。

## 最终业务需求

1. 日志接入与查询
   - 批量接收各业务服务的结构化日志。
   - 按 Trace ID、Request ID、服务、环境、级别、错误码和时间范围查询日志。
   - 根据 Trace ID、Span ID 和 Parent Span ID 还原跨服务调用链。
2. 异常发现
   - 识别同一错误指纹持续出现。
   - 识别请求量同比突增、同比骤降和无流量。
   - 识别错误码数量、错误码占比和整体失败率突增。
3. 故障管理
   - 将同类异常归并为稳定的 Incident，避免每个统计窗口重复建单。
   - 支持故障分派、处理中、解决、重新打开和解决结论记录。
   - 保存 Incident 与代表性 Trace 的关系，支持从故障定位日志，也支持从 Trace 反查故障。
4. 自动诊断
   - Incident 触发诊断任务，向诊断 Agent 提供故障指标和关联日志上下文。
   - 管理诊断的开始、完成、超时、取消和重试状态，防止重复结果覆盖。
5. 恢复与通知
   - 指标连续多个窗口恢复正常后自动解决 Incident；相同异常再次发生时重新打开。
   - 对故障创建、恢复等事件发送幂等通知，并记录发送结果和失败重试。
6. 消息可靠性
   - Kafka 消费失败时区分可重试和不可重试错误。
   - 重试耗尽或不可处理的消息进入死信记录，支持查询、人工重放和再次失败隔离。
7. 生产运维
   - 支持数据库版本迁移、多实例并发控制、数据保留、策略配置、权限控制和审计。

## 当前已完成

- 已按 `interfaces`、`application`、`domain`、`infrastructure` 划分 Logging、Incident、Diagnosis 和共享消息代码。
- 已实现日志批量接入、字段校验、错误分类、查询，以及 Request、Trace、Span 的关联查询。
- 已实现重复错误、请求量同比变化、无流量、错误码数量/占比和失败率异常检测。
- 已实现稳定 Incident、状态流转、分派、解决结论、自动恢复、再次打开和代表性 Trace 关联。
- 已实现内存统计窗口和 MySQL 原子累加统计窗口，外部模式下可供多实例共享指标。
- 已实现诊断任务的创建、回调、完成、超时、取消、重试和重复结果幂等处理。
- 已实现 Webhook 通知、通知记录、重试和幂等键。
- 已实现 Kafka 消费重试、死信持久化、死信查询、人工重放和 `PARKED` 隔离。
- 已提供 `local` 与 `external` 两套适配器，单元测试和应用打包已通过。
- 已引入 Flyway，并用 V1 至 V4 迁移脚本替代 `schema.sql`；外部模式先迁移数据库，再由 R2DBC 执行业务访问。
- 已实现 MySQL、Kafka、Elasticsearch Testcontainers 集成测试，并通过 Maven Profile 与普通单元测试分组。
- 已为 Incident 增加乐观锁和冲突后的领域操作重放，并为通知增加跨实例领取租约。
- 已实现全局、服务、接口三级异常策略，阈值和恢复规则可通过 API 管理，Incident 会保存命中的策略及版本。

## 后续工作

### 1. 建立数据库版本迁移（已完成）

目标：新环境可以一次建库，旧环境可以安全升级，避免只依赖 `schema.sql`。

实现结果：

1. Flyway 使用 JDBC 在 external 模式启动阶段执行 DDL，R2DBC 只承担业务读写。
2. `V1` 保存原始结构，`V2` 负责 Incident 指标、关联、通知和死信能力，`V3` 增加多实例并发控制字段，`V4` 增加异常策略及 Incident 的策略快照引用。
3. 旧 `schema.sql` 已移除；后续字段、索引和约束只允许新增版本迁移。
4. 集成测试覆盖空库执行 V1 至 V4，以及已有 V1 数据升级、语义字段回填、并发字段和默认策略初始化。

### 2. 补充真实基础设施集成测试（已实现，待 Docker 环境执行）

目标：验证实现与真实 Kafka、MySQL、Elasticsearch 的协议和行为一致。

实现结果：

1. Testcontainers 分别启动隔离的 Kafka、MySQL 和 Elasticsearch。
2. MySQL 测试验证迁移、统计窗口原子累加、Incident 持久化和自动恢复。
3. Kafka 测试验证正常消费、可重试失败、死信、人工重放和二次失败隔离。
4. Elasticsearch 测试验证 Data Stream 初始化、批量写入幂等性和 Trace 查询。
5. `mvn test` 运行单元测试，`mvn verify -Pintegration-tests` 运行容器集成测试；CI 执行后者。
6. 当前执行环境未安装 Docker，测试代码已完成编译，但容器用例仍需由 Docker 环境或 CI 完成实际运行。

### 3. 加固多实例并发一致性（已完成）

目标：多个实例同时处理同一异常、通知或状态变更时不重复执行、不互相覆盖。

实现结果：

1. `V3` 为 Incident 增加版本号，MySQL 和内存 Repository 都只允许匹配当前版本的更新。
2. 所有 Incident 修改统一传入领域操作；发生版本冲突时重新读取最新聚合并最多重放五次，避免用旧对象覆盖并发变更。
3. 通知发送前原子进入 `SENDING` 并记录实例租约；只有租约持有者能回写结果，实例宕机后其他实例可在租约到期后接管。
4. 通知幂等键使用 Incident 版本区分生命周期事件，Webhook 重复投递仍可按同一键去重。
5. 自动化测试覆盖同键并发创建、恢复与重新打开时的冲突重放、通知竞争领取、租约过期接管和 MySQL 旧版本拒绝更新。

### 4. 增加异常策略管理（已完成）

目标：不同服务、环境和接口可以使用不同阈值，而不是全部依赖全局 YAML 配置。

实现结果：

1. 建立充血的异常策略聚合，统一管理重复错误、请求量、错误码、失败率、同比周期和恢复窗口规则。
2. 通过 `V4` 持久化全局默认策略和服务、环境、接口策略；同一作用域只允许一条策略，修改使用乐观版本控制。
3. 提供策略查询、创建和修改 API；禁用某个具体作用域后，该作用域停止检测且不回退到宽泛策略。
4. 检测时按“接口策略 → 服务策略 → 全局默认”解析；重复错误按“服务策略 → 全局默认”解析，并在 Incident 中保存命中的策略 ID 和版本。
5. 单元测试覆盖领域规则、继承优先级、禁用覆盖、作用域冲突、版本冲突和检测结果的策略快照。

### 5. 增加数据保留与清理

目标：统计窗口、Trace 样本、通知和死信数据不会无限增长。

实施步骤：

1. 为各类数据定义保留周期和可配置上限。
2. 按查询方式补充时间索引。
3. 使用小批次定时清理，避免长事务和锁表。
4. 记录每次清理数量、耗时和失败原因，并验证查询性能。

### 6. 完善运维查询

目标：运维人员能够快速筛选故障并处理死信，不依赖直接查询数据库。

实施步骤：

1. 为 Incident 列表增加状态、类型、服务、环境、负责人和时间范围筛选及分页。
2. 为死信列表增加主题、状态、错误类型和时间范围筛选及分页。
3. 展示每次重放、通知和诊断的操作结果及失败原因。
4. 为关键接口补充 Prometheus 指标和告警规则。

### 7. 增加权限与审计

目标：状态变更、故障分派、死信重放和策略修改只能由授权用户执行，并且操作可追溯。

实施步骤：

1. 接入统一身份认证，区分只读、运维和管理员角色。
2. 对修改类接口和死信重放接口执行权限校验。
3. 记录操作者、操作对象、变更前后内容、时间和结果。
4. 提供审计查询并覆盖越权和重复提交测试。

## 实施顺序

按 `数据库迁移 → 真实基础设施集成测试 → 多实例并发一致性 → 异常策略管理 → 数据保留 → 运维查询 → 权限与审计` 执行。前两项先建立可靠的数据基础和验证环境，之后再扩展业务配置与管理能力，避免后续功能建立在不可升级或未经真实环境验证的数据层上。

## 完成标准

- 相同输入在单实例和多实例部署下产生一致的 Incident、通知和死信结果。
- 应用升级不会丢失或破坏既有数据。
- 日志接入、异常发现、自动恢复、诊断、通知和消息重放都有自动化验证。
- 所有修改类操作都有权限控制和审计记录。
